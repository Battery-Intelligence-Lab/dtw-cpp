Design (orchestrator; report any deviation with its reason before landing it):
1. One run description. `cluster(data, k, device="hpc", **keys)` validates `keys` as the local route does (the C++ `Config` through `_config`), then writes `job.toml`: one `key = value` line per key the caller gave (snake_case → the CLI's hyphenated name, as `parse_config` maps it; a key not given is not written, so the remote binary's own defaults apply, as W9b decided for the local route), plus `input`, `n-clusters`, `name`, `device` (`cpu`, or `gpu` for `hpc:gpu`; the C++ grammar, W10a) and `skip-rows`/`skip-cols` when set. Values: integers, floats (`repr`) and booleans bare, every string quoted with `"`, `\` and `"` escaped, control bytes as `\u00XX`, UTF-8 kept — the grammar `dtwc/cli/config.cpp:config_value` writes and CLI11's reader reads. `_HPC_KEYS` and the `skip_rows` refusal go; `delimiter` stays refused only if `dtwc_cl` has no such option (check `--help`).
2. The job. `cluster_generic.slurm` runs `"${DTWC_BIN}" --config "${DTWC_JOB}/job.toml" --output "${RESULTS_DIR}"` (the output directory is per job id, so it is the one command-line value; CLI11 lets the command line beat the file) and nothing else; its 20 parameters go. `slurm_remote.sh submit-job <rundir>` replaces `submit-cluster <20 positionals>`: `<rundir>` is the local run directory holding `job.toml` and, for in-memory data, `input.tsv` (uploaded as one directory; the envelope grammar for names and paths stays — it is the ssh/shell-injection boundary, keep it as it is). `SlurmRemoteRunner.submit_cluster` becomes `submit_job(rundir, *, device, gpu_device)`; `build_dtwc_command`, `find_dtwc_binary`, `_validate_remote_configuration`, `_normalize_choice` and `_variant_validation.py` go (the C++ Config validates; their callers outside `_hpc` are updated or deleted with them). `write_series_tsv`, `parse_labels_csv`, `preflight`, `wait`, `download_labels` and the `.env` reading stay.
3. `gpu_device=`. `cluster(..., device="hpc:gpu", gpu_device="a100")` (a Python-only key, refused for a local device with InvalidInput; `hpc:gpu` without it asks for any GPU of compute capability 8.0 or newer) maps to the sbatch request the wrapper adds at submit time: `--gres=gpu:<type>:1` where ARC documents the type (A100), otherwise `--gres=gpu:1 --constraint=<ARC's sku/gen constraint>` (RTX A6000, L40S, H100 have no gres type: the S1 note). Fetch https://arc-user-guide.readthedocs.io/en/latest/_sources/arc-systems.rst.txt for the exact spellings and cite the lines in your record; the mapping is one table in `_hpc.py`, tested as data. The job picks the binary by name: `build-<gpu_device>/bin/dtwc_cl` when given, else `build-htc-gpu` for `gpu`, else `build-htc-cpu` (no more "newest build wins" globbing). `slurm_remote.sh build htc-gpu --gpu-device <type>` submits the build job with the same GPU request, so `build-arc.sh` runs on that node and its existing native detection (`CMAKE_CUDA_ARCHITECTURES=native`, `-march=native`) builds for it into `build-<type>`; without `--gpu-device` the build stays portable (S1: today's `build` never asks for a GPU, and `htc-gpu`'s "native" branch never runs). The P100/V100/RTX8000 types are below the floor: refuse them locally naming the floor.
4. `scripts/slurm/jobs/{cpu,gpu,checkpoint,parquet}_test.slurm` → one `smoke.slurm` with `MODE=cpu|gpu|checkpoint|parquet` (`submit-cpu/-gpu/-checkpoint/-parquet` → `submit-smoke <mode>`); the GPU mode carries the floor constraint of item 3 so it cannot land on a refused V100. The two UCR benchmark jobs stay (`submit-benchmark-gpu [type]` uses the same mapping table through the wrapper).
Keep: the local CPU/GPU routes untouched (`cluster()` outside the `hpc` branch, `_clustering.py`); the CLI unchanged; the ssh/injection tests of `TestSlurmLastMile` pass re-pointed at `submit-job` (they drive the real bash wrapper with fake `ssh`/`sbatch`); the packaged-wrapper tests (`TestPackagedWrapper`).
