Design (orchestrator; report any deviation with its reason before landing it):
1. Three targets, one library name kept for consumers. `dtwc_core` (STATIC): base, core, algorithms, mip (its linked solver stays optional as now), Problem, Problem_IO, scores, initialisation, checkpoint, the text reader (`io/read_data.cpp`'s CSV/TSV/folder path and `io/parse_number.cpp`), the enums/types/detail headers, cuda and metal (each behind its switch, as now). `dtwc_io` (STATIC): the Arrow IPC and Parquet readers (`arrow_c_data.cpp`, nanoarrow, the Parquet chunk reader) and nothing else; Arrow links on it alone. The CLI target links `dtwc_core`, `dtwc_io`, CLI11 and fkYAML, and owns `cli/config.cpp`, `cli/run.cpp` and `api.cpp` (the facade is the CLI's; if a test or example needs `dtwc::run`, it links the CLI's object library — say which). `dtwc++` stays as an INTERFACE target that links all three, so `tests/`, `examples/`, `benchmarks/` and any external `find_package` consumer keep their link line; the Python module and the MEX link `dtwc_core` only.
2. The reader split without a silent fallback. `dtwc::read_data` in the core reads text and folders of text; a `.parquet` / `.arrow` / `.feather` path it is given raises the typed error it raises today when Arrow is absent (naming the format and that this build's reader has no Arrow; the bindings already route those formats to pyarrow / parquetread and refuse the rest). The CLI dispatches by extension to `dtwc::io::read_arrow` (dtwc_io) and otherwise to the core reader; `DTWC_HAS_ARROW` / `DTWC_HAS_PARQUET` become dtwc_io's PUBLIC definitions (the tests that read them keep working through `dtwc++`). No registration hooks, no weak symbols, no runtime plug-in: the dispatch is one `if` in the CLI's reader entry.
3. Headers. Every folder lists its public headers in a `FILE_SET HEADERS` (`BASE_DIRS` the `dtwc/` directory, never the repo root; CMake 3.26 is already the minimum); the 41 headers listed nowhere (count them: headers under `dtwc/` that no `target_sources` names) are listed in their folder's set, or deleted if nothing includes them (`git grep` proof per header). `target_include_directories(... PUBLIC .)` goes where the file set's base directory replaces it; `install(TARGETS …)` of the CLI stays as it is (no library install is added: out of scope).
4. Keep: compile commands of every unchanged source identical before and after (L2a's method: diff `compile_commands.json` per source, flags sorted); `dtwc_cl`'s outputs byte-identical on the 25 CLI runs of the W9e brief (same inputs, `diff -r`), conformance digit-identical (the one Mac silhouette ulp, D-19); every ctest target, example and benchmark still builds and links through `dtwc++`; the Metal and CUDA folders untouched beyond their target name (the orchestrator runs the second short Mac pass afterwards); `scripts/codegen_probe.cpp` / `test_codegen_no_calls` still find `dtwc/core/dtw_dispatch.cpp`'s flags (they read the compile commands: check `scripts/codegen_report.py`).
