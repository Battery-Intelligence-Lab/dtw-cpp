# Automatic mid-fill checkpointing (2026-09-02)

Build/gate: `build/highs-1151` (clang + Ninja + Release, HiGHS ON, llfio ON, Arrow OFF).

## Final semantics (5 lines)

1. `Problem::checkpoint` (`CheckpointOptions`) is now read by `fill_distance_matrix()`; `enabled=false` (default) leaves the fill unchanged apart from one `if`.
2. `save_interval` = **completed matrix ROWS between automatic saves**; the BruteForce fill runs consecutive disjoint row blocks of that size, and publishes one generation after every block, the last included, so `ceil(N/save_interval)` generations exist after a complete fill.
3. `enabled` with `save_interval < 1`, an empty `directory`, or `MmapDistanceMatrix` storage raises `InvalidInput` from the first statement of `fill_distance_matrix()`, before any distance is computed.
4. `DistanceMatrixStrategy::Pruned` + `enabled` is downgraded to `BruteForce` (verbose note, same pattern as the existing exact-hint downgrades); CUDA/Metal get exactly one save after the switch, guarded by `effective != BruteForce`.
5. A throwing save propagates out of `fill_distance_matrix()`: computed cells stay resident and the previously published generation stays valid.

## Load-bearing bug found and fixed [confirmed]

`fillDistanceMatrix_BruteForce()` called `m.resize(N)` **unconditionally**, and `resize()` re-fills every packed slot with NaN. So `load_checkpoint()` followed by `fill_distance_matrix()` silently discarded the restored matrix and recomputed every pair — resume never worked through the fill entry point. `core::fill_distance_matrix_pruned` had already been fixed for exactly this (`pruned_distance_matrix.cpp:80-85`) with a comment claiming it "Matches the brute-force fill (Problem.cpp)"; it did not. Now guarded by `if (m.size() != N)`.

Evidence: real CLI on `data/dummy` (N=25), `--checkpoint <dir> --checkpoint-interval 2`: first run 15.09 s, `generations/` = 14 (13 mid-fill blocks + the CLI's existing end-of-run save); second run with the same dir printed `Resumed from checkpoint:` and finished in **0.15 s**. Before the fix, unit test 10 failed with `10020.99910970118617115 == 901.0` (a poisoned cell recomputed).

## Binding surface for Python / MATLAB (not bound here)

- Member: `Problem::checkpoint`, type `dtwc::CheckpointOptions`, public read-write.
- Fields / defaults: `directory: str = "./checkpoints"`, `save_interval: int = 100`, `enabled: bool = False`.
- Python: `nb::class_<dtwc::Problem>` needs `.def_rw("checkpoint", &dtwc::Problem::checkpoint, nb::rv_policy::reference_internal)` so `prob.checkpoint.enabled = True` mutates the Problem in place; without `reference_internal` the getter yields a copy and the assignment is silently lost. Add a test asserting in-place mutation survives, plus `prob.checkpoint = dtwcpp.CheckpointOptions(...)` whole-struct assignment. `CheckpointOptions` itself is already bound (`_dtwcpp_core.cpp:1265-1273`); only the docstrings need updating (`save_interval` is no longer reserved).
- MATLAB: `dtwc.CheckpointOptions` already builds the struct; `dtwc_mex` must accept it and write the three fields onto the `Problem` before any fill/cluster call.
- Errors both layers must surface (exact C++ messages, all `dtwc::InvalidInput`):
  - `Problem::fill_distance_matrix: checkpoint.save_interval must be at least 1 row when checkpoint.enabled; got <n>.`
  - `Problem::fill_distance_matrix: checkpoint.enabled requires a non-empty checkpoint.directory.`
  - `Problem::fill_distance_matrix: automatic checkpointing requires dense distance storage. Mapped storage is already durable on disk; the dense checkpoint format is for heap matrices.`

## Proposed CHANGELOG bullets (Unreleased)

- Added automatic mid-fill checkpointing: `Problem::checkpoint` (`CheckpointOptions`) is now consumed by `fill_distance_matrix()`. With `enabled`, the exact BruteForce row schedule runs in consecutive blocks of `save_interval` completed rows and publishes one immutable generation after each block, the last included. `enabled` requires dense storage and `save_interval >= 1`; either violation is an `InvalidInput` raised before any distance is computed, and `DistanceMatrixStrategy::Pruned` is downgraded to `BruteForce`. Default `enabled=false` leaves the fill unchanged.
- Fixed `fill_distance_matrix()` discarding a restored checkpoint: `fillDistanceMatrix_BruteForce()` resized the dense matrix unconditionally, and `DenseDistanceMatrix::resize()` re-fills every packed slot with NaN, so a `load_checkpoint()` + `fill_distance_matrix()` resume recomputed **every** pair instead of only the missing ones. The resize now runs only when the dimension actually changes, matching `core::fill_distance_matrix_pruned`. Measured on `data/dummy` (N=25): resume 15.09 s → 0.15 s.
- Added CLI `--checkpoint-interval <rows>` (TOML key `checkpoint-interval`), which enables automatic mid-fill saving and requires `--checkpoint <dir>`. `--checkpoint` alone keeps the previous save-once-at-the-end behaviour.
- Supersedes the previous "Known limitation" entry stating that `CheckpointOptions::save_interval` is inert and that nothing checkpoints from inside `fill_distance_matrix()` (CHANGELOG.md:304-307).

## Proposed LESSONS.md entry

**`resize()` on a distance matrix is a wipe, not a growth.** `core::DenseDistanceMatrix::resize()` calls `data_.assign(packed_size(n), NaN)` — it destroys every computed cell even when `n` is unchanged. Any fill entry point that resizes unconditionally silently invalidates a restored checkpoint or a warm matrix, and the symptom is only "slow", never "wrong". Guard every such call with `if (m.size() != n)`. The pruned builder had already been fixed for this and its comment asserted the brute-force path matched; it did not, for months. Corollary: a comment claiming another code path "matches" is not evidence — grep the other path.

## Residual uncertainty / most-likely-wrong claim

The claim I would most expect to be challenged: that `enabled=false` is *byte-identical* to previous behaviour. The added `if` is free, but the conditional resize is a genuine behaviour change on the disabled path too — a caller that pre-populated the dense matrix and then called `fill_distance_matrix()` used to get everything recomputed and now keeps its values. That is the bug fix, not a regression; `cpp_conformance` and 31 focused tests agree, but no test pins the old wipe semantics, so nothing would have caught it if it were wrong.
