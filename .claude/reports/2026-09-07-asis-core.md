### 2b. The distance-matrix fill

**Entry.** `Problem::fill_distance_matrix()` `[Problem.cpp:856]`. Serial missing-data pre-scan first
`[Problem.cpp:891-918]`: `Error` rejects any NaN by series name; `Interpolate` rejects any *all-NaN*
series so `interpolate_linear` cannot throw inside the OpenMP region. Then `Auto` resolves via
`pruned_strategy_applicable` `[Problem.cpp:741-753]` — Standard/ADTW ∧ `MissingStrategy::Error` ∧ dense
storage ∧ f64 ∧ `band ≥ 0` ∧ `N ≥ 64`. Four downgrades follow (missing strategy `:946`, mmap storage
`:957`, checkpointing `:968`, f32 `:984`).

**Route A — BruteForce** `[Problem.cpp:781-845]`:
conditional `resize` (never unconditional — it NaN-wipes, `distance_matrix.hpp:51-55`) `[:792-796]` →
diagonal zeros `[:799-803]` → `fill_row` lambda `[:808-826]` → `run_openmp(fill_row, N, true, 8)` `[:828]`.
**Decomposition: one row `i` per task**; each task writes only cells `(i, j>i)`, so writes are disjoint
without any synchronisation. Per cell: `visit_distmat(is_computed)` → `dtw_fn_(si, series(j))` →
`visit_distmat(set)`. With `checkpoint.enabled`, rows are processed in blocks of
`checkpoint.save_interval` with a serial save between blocks `[:835-844]`.

**Route B — Pruned** `[Problem.cpp:1025-1041]` → `core::fill_distance_matrix_pruned`
`[pruned_distance_matrix.cpp:53]`:
rejects mmap storage `[:61-65]`; **conditional** resize `[:84-85]`; strategy→flags switch `[:96-123]`;
parallel `SeriesSummary` pass `[:127-133]`; parallel `Envelope` pass `[:144-150]`; parallel
`WebbEnvelope` pass `[:151-157]`; `nn_dist` array of `std::atomic<double>` `[:161-163]`; diagonal
`[:166-167]`. **Decomposition: contiguous blocks of the linear pair index `k`**, with
`block_count = min(pair_count, nthreads·8)` `[:182-185]`; each block decodes `k → (i,j)` through the
SSOT `dtwc::detail::decode_pair` `[:209-210]`; already-computed cells are honoured and seed the NN
thresholds `[:217-222]`; the LB cascade runs `[:226-252]`; the DTW is attempted with the NN cutoff and,
on the `maxValue` sentinel, **recomputed exactly** `[:279-285]`. Results are written with `dm.set`
`[:296]` and NN thresholds updated with two relaxed CAS loops `[:299-300]`. Counters are block-local
and reduced once `[:194-197, :303-306]`. `run_openmp(compute_pair_block, block_count, true, 8)` `[:308]`.

**Route B′ — standalone** `compute_distance_matrix_pruned` `[pruned_distance_matrix.cpp:322]`:
**row decomposition** (`compute_row`, `run_openmp(…, N, true, 8)` `[:374, :449]`), Kim+Keogh only,

**Mmap storage.** `MmapDistanceMatrix::set` `[mmap_distance_matrix.hpp:682-701]` additionally issues a

### 2c. f32 vs f64

Two parallel worlds, resolved once at bind time:

- `Problem` holds `dtw_fn_` (`std::function<data_t(span<const data_t>,span<const data_t>)>`) and
  `dtw_fn_f32_` (`…<double(span<const float>,span<const float>)>`) `[Problem.hpp:130-131, 137-138]`.
- `resolve_dtw_fn<T>` is explicitly instantiated for `data_t` and `float` only

- Compute stays in `T`; the public boundary is normalised by `normalize_public_distance`
  `[public_distance.hpp:19-30]`, which maps `float::max()` (the f32 no-path sentinel) to

- The only genuinely divergent path is WDTW: f64 reads `Problem::wdtw_weights_cache()`

- f32 additionally passes `validate_active_variant_params_f32` `[distance_semantics.hpp:99-100`,

- The distance matrix is always `double` `[storage.hpp:24]`; f32 is a *storage* choice only.
- `Problem::series(i)` throws on an f32 store `[Data.hpp:56]`, which is why the whole LB/pruned route is

## 3. Performance-critical structures — DO-NOT-BREAK list

**DNB-1 — One kernel family, Cost/Cell as *template* parameters.**
`dtw_kernel_{full,linear,eap,banded}` `[dtw_kernel.hpp:214, 248, 323, 420]` take `Cost` and `Cell` by
type, so the pointwise cost inlines into the recurrence body. Rationale: `design.md:15` ("Variants are
expressed through Cost/Cell policies, not copy-pasted recurrence loops"), `cpp-style.md:30` ("No virtual
dispatch in hot paths — use CRTP or templates"), and `LESSONS.md:369` (adding `Cell::seed` for AROW
required touching no existing policy).
*Cost of a naive cleanup:* replacing `Cost`/`Cell` with `std::function` or a virtual interface converts
one inlined multiply-add into an indirect call **per cell** — an O(n·m) regression, not O(1).

**DNB-2 — Orientation to `n_short ≤ n_long` before every kernel call.**
Repeated in 12 wrappers (e.g. `warping.hpp:92-96`, `warping_adtw.hpp:82-86`, `warping_wdtw.hpp:122-126`,
`warping_missing.hpp:165-169`, `warping_missing_arow.hpp:68-74`, `soft_dtw.hpp:131-134`, `msm.hpp:73`,
`twe.hpp:64`). It is a **kernel precondition** `[dtw_kernel.hpp:30-32]`, not a stylistic accident: the
rolling buffer is sized on the short axis, so mis-orienting doubles the working set and can push it out
of L1. All current costs are symmetric, so the swap has no semantic effect.

**DNB-3 — `thread_local` scratch, resize-never-shrink.**
`dtw_kernel.hpp:220, 255, 346, 438, 440`; `msm.hpp:75`; `twe.hpp:73`; `warping.hpp:618`;
`warping_ddtw.hpp:187, 210, 245, 259`; `warping_wdtw.hpp:152-154`; `soft_dtw.hpp:172, 207`;
`dtw_dispatch.cpp:149`. Rationale: `design.md:26`, `cpp-style.md:38`. `std::vector::resize` down does not
release capacity, so after the first pair per thread the fill is allocation-free.
*Cost of a naive cleanup:* local `std::vector`s reintroduce one or two mallocs *per pair* inside an N²
loop.

**DNB-4 — Series are viewed, never copied.**
`Problem::series(i)` returns `std::span<const data_t>` `[Problem.hpp:396` → `Data.hpp:53-58]`; every
kernel wrapper takes `(ptr, len)` or `span`. `dtw_fn_` is `std::function<double(span,span)>`
`[Problem.hpp:130]`.
*Cost of a naive cleanup:* a `std::vector` parameter anywhere on this chain copies both series per pair
— for 8 K samples, 128 KB of memcpy per distance on a memory-bound workload.

**DNB-5 — Lock-free fill by non-overlapping decomposition; no matrix-level synchronisation.**
`DenseDistanceMatrix` deliberately has **no** locks and **no** atomics, documented as a contract
`[distance_matrix.hpp:38-41, :63]`; the brute row decomposition `[Problem.cpp:805-807]` and the pruned
pair-block decomposition `[pruned_distance_matrix.cpp:292-296]` both restate it. Rationale:
`design.md:25`, `cpp-style.md:39`.
*Cost of a naive cleanup:* any mutex or `omp critical` around `set()` serialises N²/2 writes.

**DNB-6 — EAPruned's relaxed prune threshold.**
`thr = ub + |ub|·(n_long·16·ε)` `[dtw_kernel.hpp:343-344]`. `LESSONS.md:95` records that a no-slack
threshold returned `+inf` on ≈1/200 pairs under the build's `-fassociative-math`; relaxing a prune
threshold only *adds* cells, so exactness is preserved. **The factor 16 is regression-tested, not
derived** (`LESSONS.md:95`, PLAN R2-D4). Do not tighten it without the artifact.
Provenance: `ea6615d` "feat: EAPruned exact DTW cell-pruning kernel (Task 5.4)" (`git log -S dtw_kernel_eap`).

**DNB-7 — Initialiser-list `std::min({a,b,c})` in the live recurrences.**
`dtw_kernel.hpp:60, 77, 176`; `msm.hpp:94`; `twe.hpp:94`. `cpp-style.md:31-36` explicitly *withdraws* the
old "prefer nested `std::min`" rule: the 2.45–3.14× win at `65e249b` was specific to the retired legacy
kernels and `BM_dtwFull_L/4000` was unchanged (1.006×). Do not rewrite these on the stale rule.

**DNB-8 — `resolve_dtw_fn` binds once, not per call.**
`Problem::rebind_dtw_fn()` `[Problem.hpp:213]` calls `resolve_dtw_fn<T>` `[dtw_dispatch.cpp:337]`, which
resolves `{variant × missing_strategy × ndim × T}` at bind time; the returned closure has **zero**
branches on those axes `[dtw_dispatch.hpp:6-11]`. Every `require_univariate`/`InvalidInput` guard sits
in the *builder*, outside the closure `[dtw_dispatch.cpp:66, 260, 289, 300, 318-323]`. Rationale:
`LESSONS.md:99` — an exception thrown inside an OpenMP region is UB, so validation must be serial and
bind-time. The `std::function` indirection is a per-*pair* cost, accepted at `design.md:16`.
Provenance: `e1cb8a3` (`git log -S require_univariate`).

**DNB-9 — Unnamed `#pragma omp critical` on the exception path, plus the CMake scanner.**
`parallelisation.hpp:136-148` carries a 12-line comment; `CMakeLists.txt:94-115` fails the configure if
any header uses the *named* form. Rationale: `LESSONS.md:1340-1351` — a named critical emits a COMMON
`.gomp_critical_user_<name>` into every including TU, which breaks GCC LTO links against `libdtwc++.a`
(binutils PR ld/32083, GCC PR lto/116361); confirmed on GCC 13.3 / binutils 2.42.
Do not name it; do not delete the scanner.

**DNB-10 — Region-local `num_threads(...)`, never `omp_set_num_threads`.**
`parallelisation.hpp:112-124` and `run` `[:190-197]`. The comment at `:187-189` states the reason: a
process-wide setter made `pruned_distance_matrix`'s `block_count` `[:183-184]` call-order dependent.
Provenance: `e1cb8a3` (`git log -S "num_threads(nthreads)"`). Closes prior finding A8.

**DNB-11 — `MmapDistanceMatrix`'s two atomic digest lanes (a deliberate cost, not an oversight).**
`set()` `[mmap_distance_matrix.hpp:682-701]` performs a release fence + two `fetch_xor` on
`row_digests_[row*2 + lane]`. Its correctness rationale is at `:680-697` (disjoint cells sharing a row
digest). **This is the one place in the fill where threads contend**, and all pairs of the same row share
the same two words. Do not "simplify" the XOR into a non-atomic update; do not assume the dense path's
zero-atomic profile carries over to mmap storage (§6, D3).

**DNB-12 — `volatile double total_` in `OrderedMedoidObjective`.**
`medoid_assignment_policy.hpp:121`, rationale at `:69-76`: the build enables FP reassociation, but the
published medoid objective is a cross-route byte contract, so accumulation order is pinned.
Provenance: `1eb8609` "fix: enforce medoid assignment contract". It costs a store+load per point — keep
it, but record it as a *known* determinism cost rather than an accident.

**DNB-13 — `decode_pair` as SSOT, FP64 seed + `while` corrections.**
`detail/decode_pair.hpp:50-86` (+ the MSL twin `:99-130`). Comments `:14-21` and `:69-71` record that the
retired copies (`int32` CUDA, `float` Metal) produced out-of-bounds pairs for N > ~4096 and overflowed
`i*(2N-i-1)` at N ≥ 46341, and that a **single `if`** up-correction was the bug. Do not replace the
`while` loops with `if`, and do not re-derive a local copy — `pruned_distance_matrix.cpp:207` records one
such regression already being removed.

**DNB-14 — Branchless LB_Keogh accumulation.**
`lower_bound_impl.hpp:191-201`, comment `:194-197`: `max(0,eu) + max(0,el)` decomposes into two
independent `vmaxpd` instead of a dependent nested-`max` chain. `CHANGELOG.md:1601` records 3.2–4.3×.
The `#if defined(_MSC_VER)` split `[:185-190]` exists because MSVC rejects `reduction` on `omp simd`.

**DNB-15 — Three-pass z-normalisation (deliberately *not* König–Huygens).**
`z_normalize.hpp:9-20` states the reason: the one-pass identity suffers catastrophic cancellation when
`mean ≫ stddev`, and the three-pass form yields exact zero for constant series.

`dtw_dispatch.hpp:37-39`, but takes the full 704-line class and stores a **reference that must outlive
the function** `[:41]`. Interface-segregation violation; also the source of the `core/ → Problem.hpp`
include `[dtw_dispatch.cpp:8]`.
*Blast radius:* `Problem::rebind_dtw_fn`, the two explicit instantiations, ~10 lambda captures. A
`DistanceConfig` value + a weight-cache reference would be a mechanical substitution.

**D2 [High] — Three overlapping "resolve a distance" mechanisms.**
(a) `resolve_dtw_fn` `[dtw_dispatch.cpp:337]` — bind-once, used by the matrix fill;
(b) `distance::dtw(…, params, …)` `[distance.hpp:95]` — per-call switch, used by the facade;
(c) `core::dtw_runtime` `[dtw.cpp:25]` — per-call switch, used by bindings, which *delegates back* to
(b) for every non-`Error` strategy `[dtw.cpp:41-45]`. Three places encode "which variant means what",
and they already disagree: (b) **returns from the missing-strategy switch before ever reading
`params.variant`** `[distance.hpp:104-123]`, so `DDTW + ZeroCost` would silently run Standard DTW —
survivable only because `validate_variant_missing_semantics` `[:102]` rejects that combination first.
Any new variant must be added in three places or one of them silently degrades.
*Blast radius:* `distance.hpp`, `dtw.cpp`, `dtw_dispatch.cpp`, both binding layers.

**D3 [High] — The two distance-matrix implementations have incompatible concurrency profiles behind one
`std::variant`.** `DenseDistanceMatrix::set` is a plain store `[distance_matrix.hpp:64-68]`;
`MmapDistanceMatrix::set` is a store + release fence + two `fetch_xor` on words **shared by every pair in
the row** `[mmap_distance_matrix.hpp:682-701]`. The fill code dispatches through `visit_distmat`
`[Problem.cpp:812-823]` and is written to the *dense* contract `[Problem.cpp:805-807]`. Every
`std::visit` is also a runtime branch **per pair, twice** (`is_computed` then `set`).
*Blast radius:* `Problem::fillDistanceMatrix_BruteForce`, `dist_by_ind`, all `visit_distmat` call sites.

**D4 [High] — `Problem`'s brute-force fill decomposes by row, so load is triangular.**
`run_openmp(fill_row, N, true, 8)` `[Problem.cpp:828]`: row 0 costs `N-1` distances, row `N-1` costs 0.
`schedule(dynamic, chunk)` with `chunk = N/(nthreads·4)` `[parallelisation.hpp:114]` mitigates but does
not remove the tail; the last chunk of rows is nearly free while the first is nearly `N` pairs. The
pruned path already solved this with pair-index blocks `[pruned_distance_matrix.cpp:200-205]`.
`[inferred]` — confirmable by timing per-thread pair counts at large N.

**D5 [Medium] — LB machinery is a large, evidence-contradicted subsystem.**
`lower_bound_impl.hpp` is 928 lines — the second-largest file in scope — and `LESSONS.md:160` records:
*"The 'Pruned' distance-matrix strategy is a PESSIMISATION for an exact matrix — it does STRICTLY MORE
work than BruteForce"*, with the mechanism (the abandon returns the sentinel, never the value, so every
abandoned pair is recomputed). `LESSONS.md:24` generalises it; `LowerBoundStrategy.hpp:21-27` restates it
in the header. Yet `Auto` still resolves to `Pruned` whenever `pruned_strategy_applicable`
`[Problem.cpp:741-753]` holds.
*Blast radius:* `Problem::fill_distance_matrix`, `pruned_distance_matrix.*`, `LowerBoundStrategy`,
TADPole (which uses its own bound).

**D6 [Medium] — `dtwc::solver` types live in `types/`.**
`types/types_util.hpp:17-26` and `types/element_types.hpp:13-76` define MIP tolerances and sparse
triplets in namespace `dtwc::solver`, but sit in the generic `types/` directory and are pulled in by
`types/types.hpp:12` → `utility.hpp:17`. `types_util.hpp` also uses `std::abs`/`std::round` `[:23, 25]`
without including `<cmath>`. Misplacement + hidden coupling; belongs in `mip/`.

**D7 [Medium] — Cache-line sharing in the standalone pruned reduction.**

**D8 [Medium] — Stale-binding hazard on public mutable fields.**

## 9. Extension points today

**Compile-time (the fast, intended path).** A new pointwise cost is a struct with
`T operator()(size_t row, size_t col) const noexcept` `[dtw_cost.hpp:5-6]`; a new recurrence is a struct
with `combine(diag, up, left, cost, i, j)` and `seed(cost, i, j)` `[dtw_kernel.hpp:12-28]`. Both are
passed as **template parameters** to `dtw_kernel_{full,linear,banded}` `[dtw_kernel.hpp:214, 248, 420]`,
so they inline. `LESSONS.md:369` records that adding `seed` for AROW required touching no existing policy
— new contract methods with defaults are additive.
*Cost:* zero per cell; one template instantiation per (Cost × Cell × kernel × T) combination.
*Limitation:* `dtw_kernel_eap` `[:323]` takes **only** a `Cost`, no `Cell` — the pruning argument
`[:290-321]` relies on the standard min-of-3 recurrence and non-negative costs, so ADTW/WDTW/Soft cannot
use it. Correct and documented, but it means the fastest unbanded kernel is Standard-only.

**Runtime, per Problem (the supported user-facing path).** Set `variant_params` / `missing_strategy` /
`band` and `resolve_dtw_fn<T>` `[dtw_dispatch.cpp:337]` builds one `std::function` closure.
*Cost:* one indirect call per **pair**, accepted at `design.md:16` and prior-review H7. This is where all
`{variant × missing × ndim × T}` dispatch happens, once.

**Runtime, per call (bindings).** `core::dtw_runtime(x, nx, y, ny, DTWOptions)` `[dtw.hpp:73]` and
`distance::dtw(x, y, params, band, metric, missing)` `[distance.hpp:95]`.
*Cost:* 4 validations + 2 switches per call.

**String-typed dispatch.** Exactly one entry point: `parse_metric_token`
`[distance_semantics.hpp:24]`, accepting `{l1, squared_euclidean, sqeuclidean}`. Everything else is
enum-typed with a `validate_*` guard `[selector_validation.hpp:13-69]`.

**What a user CANNOT inject today.**

1. **A custom pairwise distance into a `Problem`.** `dtw_fn_` is `private` `[Problem.hpp:137]` and
   `rebind_dtw_fn()` unconditionally overwrites it from `resolve_dtw_fn` `[Problem.hpp:213]`. There is no
   `set_distance_function`. Every distance must be one of the seven `DTWVariant` values.
2. **A custom Cost/Cell through the runtime API.** The policies are template parameters, reachable only
   by recompiling against `dtw_kernel.hpp`. `DTWVariant` `[dtw_options.hpp:32-41]` is a closed enum with
   guards in five places (`selector_validation.hpp:13`, `variant_validation.hpp:102`, `distance.hpp:125`,
   `dtw.cpp:56`, `dtw_dispatch.cpp:360`), so adding a variant is a five-file change.
3. **A custom lower bound.** `fill_distance_matrix_pruned` switches on a closed enum
   `[pruned_distance_matrix.cpp:96-123]`.
4. **A custom distance-matrix storage.** `Problem::distMat` is a two-alternative `std::variant`
   `[pruned_distance_matrix.cpp:61]`, not a concept.

`[inferred]` A user-supplied `std::function<double(span,span)>` on `Problem` would be a ~5-line addition
with no hot-path cost, since `dtw_fn_` is already a `std::function` — but it would need a policy for
`wdtw_weights_cache_` invalidation and for the mmap fingerprint identity
`[mmap_distance_matrix.hpp:508-514]`, which currently hashes the *enumerated* configuration.

## 10. Open questions for the designer

1. **Is `Pruned` a default or a diagnostic?** `LESSONS.md:160` proves it does strictly more work than
   BruteForce for an exact matrix, yet `Auto` still selects it `[Problem.cpp:924-926]`. If it stays a
   diagnostic, `lower_bound_impl.hpp` (928 lines) and `LowerBoundStrategy` (7 values) are a large surface
   for a non-default path; if it becomes NN/TADPole-only, most of §7's dead LB entry points become the
   *intended* API and should be wired, not deleted. **This is the single biggest scoping decision in the
   core.**

2. **What is the right dependency for `resolve_dtw_fn` and `fill_distance_matrix_pruned`?** Both take
   `Problem` (§4a). A `DistanceConfig` value object + a `SeriesSource` view would remove both
   `core/ → Problem.hpp` edges. Does the design want that, or does it want `core/` and `Problem` to be
   one layer?

3. **One resolver or three?** (§6.1 D2.) `resolve_dtw_fn`, `distance::dtw(…params…)` and `dtw_runtime`
   each encode the variant/missing cross-product. Can (b) and (c) be expressed as *"build the closure,
   call it once"*? That would make the fill and the pairwise API provably identical, at the cost of one
   `std::function` construction per one-shot call.

4. **Should mmap storage share the fill code with dense storage?** Their write contracts differ by two
   atomic RMWs per cell on shared words (§6.1 D3). Options: a separate mmap fill that batches row digests
   after a row completes; a per-row digest recomputed once at join; or accepting the cost and documenting
   the throughput difference. **No measurement exists** — I could find no benchmark comparing the two
   `set()` implementations under contention.

5. **Is H1 (the banded kernel's three O(n) setup passes, `dtw_kernel.hpp:438-447`) worth fixing?**
   At `n=1000, band=5` the DP visits ~11 k cells against ~3 000 setup writes `[inferred — cell count from
   `dtw_band_bounds`]`. The prior review flagged it and explicitly said *do not land on reasoning alone*.
   Decisive test: `BM_dtwBanded/1000/50` before and after. Same question for `dtw_kernel_eap`'s two
   `assign(n_short, maxValue)` `[:347-348]`.

6. **Where do `error.hpp` / `missing_utils.hpp` belong?** They are stdlib-only and are included *upward*
   by 9 files in `core/` and `enums/` (§4b). Moving them under a foundation tier makes the include graph
   acyclic by construction; leaving them makes `core/` permanently "above" them.

7. **Should `MetricType::L2` be selectable from a token?** `parse_metric_token`
   `[distance_semantics.hpp:26-28]` cannot produce it, yet it is the only metric whose MV behaviour
   differs (`MVL2Dist`, `warping.hpp:249`, selected at `:285`). Either wire it or delete `MVL2Dist` and
   `SpanMVNanAwareL2Cost` `[dtw_cost.hpp:162]` (the latter *is* reachable, via `dtwMissing_*_mv`'s
   `metric == L2` branches `[warping_missing.hpp:269, 307]` — themselves only reachable by a direct C++
   call).

8. **What is the EAP factor 16?** `dtw_kernel.hpp:344`, `LESSONS.md:95`, PLAN R2-D4: regression-tested,
   not derived. A designer choosing the FP model needs to know whether this is a bound or a fitted
   constant.

9. **What is the invariant on `thread_local` re-entrancy?** No `Cost` functor may call a kernel that uses
   the same buffer (§8). This is currently true by construction and written down nowhere. Should it be a
   documented Cost-functor precondition, or should buffers be passed in?

10. **Is `.dtws` (`MmapDataStore`) a supported artifact?** Its header comment says "internal cache, not a
    user-facing format" `[:6]`, yet it has none of the crash-consistency machinery its sibling
    `MmapDistanceMatrix` grew (A9, still open): no publication byte, no barrier, no exclusive creation,
    unvalidated `ndim`, unchecked size arithmetic. Either bring it to parity or make it explicitly
    ephemeral (temp path, recreate-on-mismatch).

11. **Not established:** whether `dtwFull_eap` and `dtwFull_L` remain digit-identical outside the cases in
    `test_eap_dtw.cpp`; whether the row-vs-pair-block decomposition difference (§6.1 D4) is measurable at
    the target N; whether any consumer actually builds with `-ffast-math` (§6.1 D10).
