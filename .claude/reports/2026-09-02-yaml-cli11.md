# YAML `--config` via CLI11's own config interface (2026-09-02)

## Outcome

`dtwc_cl --config` accepts TOML **or** YAML. YAML is translated into CLI11
`ConfigItem`s, so CLI11 keeps ownership of precedence, validation, deprecated
aliases and `--help`. The precedence defect that killed the old `--yaml-config`
loader is pinned by a real-binary gate. Both build flavours green.

## Design as built

- `dtwc/cli/config_file.hpp` (147 lines) — `class dtwc::cli::ConfigFile :
  public CLI::ConfigBase`. `from_config(std::istream&)` slurps the stream and
  sniffs it: **the first line that is neither blank nor a `#` comment decides —
  `[table]`, or a `=` ahead of any `:`, is TOML (delegate to
  `CLI::ConfigBase::from_config`); anything else (`key: value`, `---`, `%YAML`)
  is YAML.** Verified against the sniff's real risk, a Windows path
  (`input = "C:/…"` → TOML; `input: "C:/…"` → YAML): both correct.
- YAML mapping → `ConfigItem`: top-level scalars are bare items; nested mappings
  become `parents` (CLI11 treats them like TOML tables/subcommands); a sequence
  of scalars becomes repeated `inputs`. Scalars are emitted as text
  (bool → `true`/`false`, integer → `to_string`, float → `max_digits10` so it
  round-trips, null → empty), and CLI11 does the conversion.
- Rejected with `CLI::ConfigError`: non-scalar sequence elements / nested
  sequences (names the key path), a non-mapping document root, more than one
  document in the file, and any fkYAML parse error (names the file, taken from
  `App::get_config_ptr()->results()`). **Anchors/aliases that resolve to scalars
  are accepted**, not rejected: fkYAML resolves them and they map faithfully.
- `DTWC_ENABLE_YAML` (default ON) → fkYAML v0.4.4 via CPM (`URL` + `URL_HASH`,
  `DOWNLOAD_ONLY`, `fkYAML::fkYAML` INTERFACE IMPORTED, exactly like CLI11) and
  `DTWC_HAS_YAML` on `dtwc_cl` only. With OFF, the YAML branch throws
  `<file>: built without YAML support; use TOML` — the guard is *outside* the
  `#ifdef` at the call site, so the OFF build still runs the gate.

### One behaviour change beyond the formatter

CLI11's default is to **silently ignore** a config key that matches no option —
confirmed on the pre-change binary: `not-a-real-option: 1` gave exit 0. Test (e)
requires a non-zero exit, so `dtwc_cl` now sets
`app.allow_config_extras(CLI::config_extras_mode::error)`. This applies to TOML
as well as YAML (deliberately symmetric; project rule "no silent fallbacks").
Both tracked configs (`tests/conformance/conformance.toml`,
`examples/cpp/config.toml`) use only live keys and still pass.

## Tests + results

`test_cli_config_formats` drives the real `dtwc_cl` and reads its verbose echo
of the settings actually used. YAML-ON runs 21 checks, YAML-OFF 7; the count is
pinned per flavour in `PASS_REGULAR_EXPRESSION`, so a short-circuited script
cannot pass. Cases: (a) YAML sets `n-clusters`/`method`/`band`; (b) `--n-clusters
2` on the CLI beats `n-clusters: 4` in the file — and asserts the YAML value is
*absent* from the output; (c) the conformance TOML still works through the same
`--config`; (d) `clusters:` warns `'--clusters' is deprecated, use
'--n-clusters' instead` and is honoured only when `n-clusters` is absent; (e)
unknown key → non-zero, key named; (f) malformed YAML → non-zero, file named.
YAML-OFF branch asserts the typed refusal.

**Red evidence** (the test was written after the code, so discrimination was
proved directly): running the same script with `-DHAS_YAML=1` against the
YAML-OFF binary fails at case (a) —
`yaml_applies: expected success, exit=110 … built without YAML support`.

Manual probes on the real binary (all exit 110 unless noted): nested sequence →
`method: expected a scalar value`; non-mapping root → `top level must be a
mapping…`; two documents → `expected one YAML document, found 2`; nested mapping
`solver: {mip-gap: 0.1}` → `INI was not able to parse solver.mip-gap` (parents
applied, then loudly unmatched — `dtwc_cl` has no subcommands); sequence of
scalars `method: [pam]` → exit 0; CRLF TOML → exit 0.

**Format parity arbiter:** `examples/cpp/config.yaml` and
`examples/cpp/config.toml` (minus the Parquet-only `column` key) produce
byte-identical verbose banners on the same input.

## Proposed CHANGELOG bullets (Unreleased) — not applied

- **Added:** `dtwc_cl --config` now accepts a **YAML** file as well as TOML. The
  format is detected from the file content, and YAML is parsed into CLI11's own
  configuration items, so both formats share one set of keys, validators and
  deprecation warnings — and **a value given on the command line always beats
  the file** (the removed `--yaml-config` loader did the opposite). New optional
  dependency fkYAML (MIT, header-only), build option `DTWC_ENABLE_YAML`
  (default ON); with it OFF a YAML config is refused with
  `built without YAML support; use TOML`. Example:
  `examples/cpp/config.yaml`.
- **Changed:** a `--config` key that matches no CLI option is now an error in
  **both** TOML and YAML. It used to be ignored silently, so a typo'd key ran
  with the default value.
