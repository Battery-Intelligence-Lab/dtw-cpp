|---|---|

| Python | `load(source, *, skip_cols=0, skip_rows=0, delimiter=None, name=None) -> Dataset`; `Dataset(source, *, skip_cols=0, skip_rows=0, delimiter=None, name=None)` (`python/dtwcpp/_api.py`) |

### Semantics (identical in all three)

* **Path source** — drop the first `skip_rows` **lines** of the file before
  parsing. C++ maps to `DataLoader::start_row` (verified: `start_row_` is a
  line-skip counter in `load_batch_file`/`load_folder`/`count`,
  `dtwc/DataLoader.hpp:496,535,568`), i.e. exactly the `dtwc_cl --skip-rows`
  meaning (`dtwc/dtwc_cl.cpp:1517`). Python uses `np.loadtxt(..., skiprows=)`;
  MATLAB `readmatrix(..., 'NumHeaderLines', n)`.
* **In-memory source — decision: drop the first `skip_rows` SERIES (rows), not
  reject.** Reason: a batch file's line *is* a series, so the C++ in-memory
  overload can implement the file rule exactly, and it composes with `skip_cols`
  (which already erases leading columns of in-memory rows, `api.cpp`). Rejecting
  would have made the two overloads disagree on the meaning of the same
  argument. `skip_rows >= N` is clamped to "drop everything", matching a file
  with fewer lines than `skip_rows` — `cluster()` then raises the existing
  `InvalidInput("cluster: dataset is empty.")`.
* **Validation** mirrors how each language validates `skip_cols` today, not a
  new scheme: C++ rejects negative values inside `load()` (`InvalidInput`);
  Python rejects negative/non-integer in `_validate_common` at `cluster()` time
  (`ValueError`/`TypeError`, before any side effect); MATLAB uses the same
  `inputParser` validator as `skip_cols`, so both produce the same identifier.
* **HPC (Python only):** the SLURM transport is a fixed positional argument list
  in `scripts/slurm/slurm_remote.sh` with no `skip_rows` slot. Rather than
  silently dropping it, `cluster(..., device="hpc")` raises `InvalidInput` when
  `skip_rows != 0`. Documented in the contract table. **This is the one design
  call I most expect to be challenged** — the alternative is plumbing
  `--skip-rows` through `_hpc.py` (6 call sites) *and* the bash wrapper, which
  cannot be verified on this box.

## Drift list (found, NOT fixed — beyond A and B)

Ordered by severity. Every item is source-pinned.

**Silent wrong answer**
1. `cluster(method=...)` MATLAB collapses `'pam'`, `'kmedoids'` and `'auto'`
   into one `dtwc.fast_pam` call (`+dtwc/cluster.m:67-70`). C++ (`api.cpp:361-389`)
   and Python (`_api.py:338-378`) route each name to its own algorithm.
   `method='kmedoids'` therefore runs FastPAM, and `'auto'` never switches to
   CLARA above 5 000 series.
2. `cluster(device=...)` is a per-call override in C++ (local `Env`,
   `api.cpp:315-327`) and Python (`_api.py:404-405`) but MATLAB calls
   `dtwc.device(dev)` (`+dtwc/cluster.m:36-38`), permanently mutating the global
   registry for the rest of the session.
3. `Result.save` series names: C++ writes `series_name(i)` (`api.cpp:259,268`),
   Python writes `_series_names` (`_api.py:188,195`), MATLAB hard-codes the
   ordinal (`+dtwc/Result.m:82,90`) despite having passed real names into
   `set_data` — breaks byte-identity with the CLI for named datasets.
4. `max_iter` is silently ignored by MATLAB's `clara` branch (only `'Seed'` is
   forwarded, `+dtwc/cluster.m:72-73`); `fast_clara`'s own default of 100 wins.
5. `device()` return value: C++/MATLAB canonicalise via `to_string(Device)`
   (`api.cpp:43-49,204-210`; `dtwc_mex.cpp:786-797`), Python returns the
   caller's lower-cased string (`__init__.py:236-240`), so `device("cuda:0")`
   is `"gpu"` in C++/MATLAB and `"cuda:0"` in Python.
6. `device()` source of truth: Python reads a module global `_DEFAULT_DEVICE`
   and `_sync_env` skips `hpc` (`__init__.py:198,210-212,243-245`), so after
   `dtwcpp.device("hpc")` in-process C++ still sees `Env` on `cpu`.

**Missing feature**
7. `onebatch`, `lrcore`, `tadpole` are valid methods in C++/Python but raise
   `dtwc:invalidArgument` in MATLAB (`+dtwc/cluster.m:85-88`).
8. `Result.score` after a matrix-free run: C++/MATLAB score off the retained
   `Problem`; Python raises `InvalidInput` because `distance_matrix is None`
   (`_api.py:129-133`, set at `_api.py:450`).
9. `CheckpointOptions` fields align in all three, but neither binding exposes
   `Problem::checkpoint` (`Problem.hpp:309`) — no `def_rw("checkpoint")`, no
   `Problem_set_checkpoint` — so automatic mid-fill checkpointing is
   C++-only.
10. `save_checkpoint`/`load_checkpoint` take a `metric` argument in C++
    (`checkpoint.hpp:73-74`) and Python (`_dtwcpp_core.cpp:1286,1299`) but not
    in MATLAB (`+dtwc/save_checkpoint.m`, `load_checkpoint.m`) — a SquaredL2
    matrix is stamped and reloaded as L1.
11. The `k <= N` guard exists only in C++ (`api.cpp:339-340`).
12. Python `Dataset.as_series()` applies `skip_cols` *after* `np.loadtxt`, so a
    non-numeric id column fails to parse; C++ `start_col` skips fields *before*
    numeric parsing. Same `skip_cols` value, different outcome on a real id
    column. (Found while writing the Python `skip_rows` test; the test uses a
    numeric id column to isolate `skip_rows`.)
13. Python and MATLAB ignore `skip_cols` entirely for **in-memory** sources
    (`_api.py` else-branch; `Dataset.m` `isnumeric` branch); C++ erases the
    leading columns (`api.cpp`). `skip_rows` is now honoured in memory by all
    three, so `skip_cols` is the odd one out.

**Cosmetic**
14. `get_device()` exists only in Python; C++/MATLAB use the zero-argument
    `device()` overload.

`MIPSettings`: all nine fields now align across `Problem.hpp:64-73`,
`_dtwcpp_core.cpp`, `dtwc_mex.cpp` — no residual drift.
