# 2026-09-30 — R1: TSan (LLVM libomp + Archer) on the race-free sweep

Question: with the `omp critical` sections of `fast_pam`, `fast_clara`, `one_batch_pam` and `tadpole` replaced
by per-thread slots and rows (R1), does ThreadSanitizer report a race in those algorithms or in
`run_openmp`, at the base (`ccd10c9`) and at the head (`091ea8b`)? Criterion set before the run: zero reports
at the head; the harness must first detect a known race (positive control) and must report the sites when
their synchronisation is removed (bite checks).

## `schedule(dynamic, chunk)` is nonmonotonic on libomp [confirmed]

The design brief assumed that with dynamic scheduling a thread's indices only increase. Probe (Windows, clang 21
with LLVM libomp, 8 threads, `end = 4096`, chunk 128, a few rows slowed by 20-300 us, 300 runs): count threads whose
executed index sequence ever decreases.

```
#pragma omp for schedule(dynamic, chunk) nowait          -> 300 threads over 300 runs
#pragma omp for schedule(monotonic: dynamic, chunk) nowait -> 0
```

Two threads, 64 rows, `schedule(dynamic, 1)`, rows below 31 slowed by 1 ms: thread 1 runs `32 33 ... 63`, then
steals `25 26 ... 31`, `21 ... 24`, `19 20`, `18`, `17`, `16`, `15`; thread 0 runs `0 ... 14`. Identical in three
runs. Hence a thread that has failed at row 32 is still handed row 31, and `run_openmp` runs it
(`if (i > slot.failed_at) continue;`). The `monotonic` modifier is not usable: MSVC `/openmp:experimental`
rejects it (`error C3022: 'schedule': invalid schedule kind of 'monotonic'`). Pinned by
`unit_test_parallelisation` "run_openmp runs the rows below a thread's own failure": skip-everything-after-the-first-failure
returns "row 32" for "row 31".
