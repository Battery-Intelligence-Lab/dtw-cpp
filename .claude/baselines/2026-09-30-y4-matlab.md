## Failures found on the first clang run, and their causes [confirmed by probe unless marked]

1. `test_dtwclustering_metric_routes_match_exhaustive_oracle`: `fast_pam(D_l1, 2, 'Seed', 42)` gave
   labels `[2 1 1 1]`, medoids `[4 1]`, cost 10, not `[1 2 1 1]`, `[3 2]`, 9. `{4,1}` is a swap-local
   optimum (every single swap costs 11 to 13, by hand); seed 43 gives `{3,2}`, cost 9, and the NInit=2
   estimator still reports it. `MaxIter=1` returns `converged=0`, so the start was not `{4,1}`.
   [inferred] cause: FasterPAM is the only swap since 3bdb5d8, and its first improving swap reaches a
   different local optimum than the steepest FastPAM1 swap did from the same start. The oracle's squared
   half (`{4,1}`, 30) did not change. Expectation updated to the FasterPAM result.
2. `test_checkpoint_dir_roundtrip`: `load_checkpoint` returned false because the file is
   `<dir>/<name>.dtwm` (Y2) and the test loaded a Problem named `ckpt2` from the file of `ckpt`.
3. `test_f22_matlab_deprecation_policy`: X2 cut the ledger from 15 to 10 rows (8995ad7) but left
   `== 15` in the pass condition, so it printed `warning_profiles=10/15` and failed. It counts the rows now
   (`aliases=10/10 ... verdict=PASS`).

## F43: llfio-ON MEX under R2024b

Outcome: **unreachable from MATLAB at ac311c4; CI's llfio stays OFF; scratch probe FALSIFIED the crash.**

- Reach [confirmed by reading]: llfio is included only by `dtwc/core/distance_matrix.cpp`, whose only
  entry is `DistanceMatrix::map`. Its only caller is `Problem::use_mmap_distance_matrix` (Problem.cpp:827),
  reached by `dtwc_cl` (cli/run.cpp:259) and Python (`_dtwcpp_core.cpp:995`). `dtwc_mex.cpp` has no
  such command; `save_checkpoint` calls `DistanceMatrix::write` and `load_checkpoint` calls
  `DistanceMatrix::read`, both plain file I/O, and a MEX matrix is always on the heap.
- Scratch probe (not committed): a `Problem_use_mmap` command added to `dtwc_mex.cpp` in an MSVC MEX
  configured as CI does except `-DDTWC_ENABLE_LLFIO=ON` (cmake printed `llfio: YES`), run under R2024b
  (private msvcp140 14.36, headers 14.50 - the archive's crash condition). Create a mapped file, fill
  (128-byte file for N=4), release, reopen the existing file, `save_checkpoint` of the mapped matrix,
  `load_checkpoint` into a fresh Problem, equal matrices: exit 0, no crash, `F43_PROBE_DONE` and
  `F43_PROBE2_DONE`. The `_DISABLE_CONSTEXPR_MUTEX_CONSTRUCTOR` workaround was therefore not needed and
  not applied. Logs: `C:/D/git/wt/tmp/Y4/f43_r2024b*.log` (scratchpad, disposable).
- A future mapped MATLAB route (W8c/W9e) must add: the MEX command; a guard in
  `cmd_Problem_set_distance_matrix` (it calls `resize` on the matrix; Python refuses a mapped matrix
  at `_dtwcpp_core.cpp:781-787`); and a CI job with llfio ON that runs the mapped test under R2024b,
  since one probe of one route is not that job. Only if that job crashes in `std::mutex` does the
  macro come in, on the TU that includes llfio (`distance_matrix.cpp`, in the library).
