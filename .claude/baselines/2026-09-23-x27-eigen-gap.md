## Registered band — written 2026-09-23 11:51 BST, before any measurement

**Subject:** `BM_dtwFull/{100,500,1000,4000}` in `bench_dtw_baseline`.

**A** = Eigen build, detached worktree of `7891157~1` (`4ed7953`).
**B** = HEAD `e784e5c` (no Eigen). **B′** = HEAD plus one candidate change to `ScratchMatrix`.

**Protocol:** interleaved rounds A, B, A, B … (at least three rounds per side),
`--benchmark_repetitions=10` per run, never two benchmarks at once. Reported: the median of the
per-run medians, and the spread of the per-run medians ((max − min) / median).

**A fix is accepted only if**, for every size:

1. median(B′) is within **±1 %** of median(A);
2. run-to-run spread of B′ is **≤ 0.5 %**;
3. the conformance output is **digit-identical** to HEAD's.

**Budget:** at most three hypotheses, each measured with the same interleaved protocol.
FALSIFIED is a result and is recorded here.

## Verdict

1. **The ~5 % gap does not reproduce** `[confirmed]`. Fresh builds of `4ed7953` (Eigen) and HEAD
   with identical flags, interleaved: HEAD −0.43 / −0.03 / −0.14 / −0.09 % (quiet run). A fresh
   build of `7891157` itself is also within noise.
2. **The hot loop is the same machine code, modulo address formation** `[confirmed]`: 17
   instructions per cell in both builds, 4 loads + 1 store, `up` carried in a register, no member
   reloads, no calls, no asserts. In-process A/B of verbatim copies of both classes: ≤ 0.11 % at
   500–4000, +0.85 % at 100.
3. **What does move `BM_dtwFull` is code placement** `[confirmed]`: shifting the *same* binary's
   code by 4 bytes, so that the first `fcmp`/`fcsel` pair of the min-of-three straddles a 64-byte
   boundary, costs **+28 … +46 %**. 8/8 split placements slow, 0/56 others. 64-byte loop
   alignment removes the cliff. This is a ~30 % cliff, not a uniform 5 %, so it does not by itself
   explain X-27's number; X-27's baseline and both attempts were measured sequentially, not
   interleaved, and this machine drifts by up to +7 % between rounds under load (below) — that is
   the most likely cause `[inferred]`.
4. **No `ScratchMatrix` change is needed or proposed.** HEAD already meets criterion 1 at every
   size; criterion 2 (spread ≤ 0.5 %) was **not** met on every side even in the quietest run
   (eigen/100 1.42 %, eigen/1000 0.64 %, head/4000 0.64 %), so a quiet re-run is owed before the
   band can be called met.
5. **Side finding** `[confirmed]`: under `DTWC_FP_MODEL=fast`, `soft_dtw_gradient` differs from the
   Eigen build in the last bit (542 values across the test shapes): the final reduction
   (`soft_dtw.hpp:264`) is vectorised width 2 × interleave 4 with Eigen but interleave 2 only
   without, and `-fassociative-math` lets the partial sums reorder. Under `strict`, every output of
   both ScratchMatrix users is bit-identical between the two builds.

## 2. The hot loop in both builds `[confirmed]`

`objdump -d --no-show-raw-insn --disassemble-symbols=__ZL10BM_dtwFullRN9benchmark5StateE`. The kernel
is fully inlined into `BM_dtwFull`; the loop below is the one taken for these sizes (the other copy
is the `int`-overflow guard path).

```text
eigen (4ed7953)                                   head (e784e5c)
100004428: asr   x16, x12, #29                    1000040dc: asr   x0, x13, #29
10000442c: ldr   d1, [x10, x16]      ; diag       1000040e0: ldr   d1, [x14, x0]          ; diag
100004430: asr   x16, x13, #29                    1000040e4: add   x0, x8, x15, asr #29   ; C + 8i
100004434: ldr   d2, [x10, x16]      ; left       1000040e8: ldr   d2, [x0, x11, lsl #3]  ; left
100004438: ldr   d3, [x14], #0x8     ; xs[i]      1000040ec: ldr   d3, [x16], #0x8        ; xs[i]
10000443c: ldr   d4, [x25, x9, lsl #3] ; ys[j]    1000040f0: ldr   d4, [x25, x10, lsl #3] ; ys[j]
100004440: fabd  d3, d3, d4                       1000040f4: fabd  d3, d3, d4
100004444: fcmp  d0, d1                           1000040f8: fcmp  d0, d1
100004448: fcsel d0, d0, d1, mi                   1000040fc: fcsel d0, d0, d1, mi
10000444c: fcmp  d2, d0                           100004100: fcmp  d2, d0
100004450: fcsel d0, d2, d0, mi                   100004104: fcsel d0, d2, d0, mi
100004454: fadd  d0, d3, d0                       100004108: fadd  d0, d3, d0
100004458: str   d0, [x11, x16]      ; C(i,j)     10000410c: str   d0, [x0, x12, lsl #3]  ; C(i,j)
10000445c..468: add, add, subs, b.ne              100004110..11c: add, add, subs, b.ne
```

- Same length (17 instructions/cell), same 4 loads + 1 store, same FP chain
  `fcmp → fcsel → fcmp → fcsel → fadd` through `d0` (`up` = last iteration's store, forwarded in a
  register by the compiler in both).
- Only difference: Eigen hoists two column base pointers (`x10`, `x11`) and uses `[base, off]`;
  HEAD hoists the column offsets and forms `C + 8i` with a shifted `add`. Both are off the
  loop-carried chain.
- Ruled out from this listing: member reload (none — `rows`/data pointer live in registers),
  missing inlining (no calls), debug asserts (none), storage order (both column-major, stride-1 in
  `i`, which is the inner loop). `ys[j]` is reloaded every iteration **in both** (the store to `C`
  may alias it) — a shared inefficiency, not a gap.

## 3. Hypotheses (three, per budget)

### H1 — allocation alignment (the earlier reviewer's guess): FALSIFIED `[confirmed]`

Eigen 5.0.1 `Memory.h:50-52` defines `EIGEN_MALLOC_ALREADY_ALIGNED 1` for `EIGEN_OS_MAC` with
16-byte default alignment (`ConfigureVectorization.h:72`, NEON), so `aligned_malloc` is plain
`malloc`. `probe/alloc_align.cpp` prints `EIGEN_MALLOC_ALREADY_ALIGNED=1 EIGEN_DEFAULT_ALIGN_BYTES=16`
and, at all four sizes, both `Eigen::MatrixXd::resize` and `make_unique_for_overwrite<double[]>`
return addresses ≡ 0 mod 16384. There is no alignment difference to explain anything.

### H2 — the accessor's codegen costs time: FALSIFIED `[confirmed]`

`probe/probe_ab.cpp`: verbatim copies of both `ScratchMatrix` classes and of `dtw_kernel_full`, one
binary, real flags, timed in alternating blocks (order rotated each block), 60 blocks × 25 ms,
results checked bit-identical. Its two hot loops are instruction-for-instruction the ones above.

### H3 — code placement: CONFIRMED as a mechanism, not as X-27's 5 % `[confirmed]`

A rebuild of the probe that moved the Eigen kernel by 80 bytes made it **+31.8 % at 500**
(460.61 vs 349.55 µs), same instructions. Sweep: a function of K nops linked in front of both
kernels (`-order_file`), K = 0 … 31, n = 500, 12 blocks each (`probe/sweep500.txt`; load ≈ 2, some
rounds noisy):

- **8/8 placements where an `fcmp`/`fcsel` pair straddles a 64-byte boundary** (loop start ≡ 0x18
  or 0x20 mod 64): 476.9 … 502.4 µs, median 482.2.
- **56/56 other placements**: 356.3 … 408.8 µs, median 373.1 (the 406–409 is one round where both
  variants were equally slow — machine noise).
- 16- and 32-byte boundaries do not matter (e.g. starts at 0x940 and 0x938 are fast); 64 does.
- Mechanism `[inferred]`: consistent with the core pairing `fcmp`+`fcsel` only within one 64-byte
  fetch block; not provable without PMU access.

### Remedy for the placement cliff — measured, not applied

Aligning loops to 64 bytes makes the loop start at offset 0, where neither pair straddles.
**Under ThinLTO the compile flag alone does nothing** — `-falign-loops=64` is accepted and ignored,
because codegen runs in the linker; it has to be passed to the LTO backend as
`-Wl,-mllvm,-align-loops=64` (ld64). Without LTO, `-falign-loops=64` works. With it, the 32-point
probe sweep is 64/64 fast (361.6 … 403.5 µs, `probe/sweep500_al64.txt`), and the real binary loses
the cliff (table above). Not proposed as a patch: it is a build-wide flag outside `ScratchMatrix`,
it fixes only this loop's *current* instruction order, and under the noisy run it did not meet
criterion 2. It needs its own band and a quiet run.

- **B (build-wide `-align-loops=64`): FALSIFIED on criteria 1 (n = 100, −1.60 %) and 2.** Criterion 3

- **No second attempt.** Alignment pins where a loop *starts*. Whether a loop is slow depends on where

- **Next, not measured:** remove the pair instead of placing it. `fminnm` (`std::fmin`) is one instruction

  post-link check with `scan.py`'s rule on `dtwc_cl` would make any split visible.
