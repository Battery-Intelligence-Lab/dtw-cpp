# 2026-10-08 — XL: x86-64 lanes at 128 bytes (16 doubles, 32 floats): clang++ PASS, cl FALSIFIED

Unit XL (PLAN phase C's lead "16 double lanes to hide the min-then-add latency"; V3's "next decisive test",
`2026-09-30-v3-arch-level.md`), from design-2.0 `1b2209d1` on `pb/XL`. Windows 11, Intel Core Ultra 9 285 (P-cores:
logical 0, 1, 10–13, 22, 23), clang++ 21.1.8 (GNU-style driver, MSVC ABI, as the main `build/`) and cl 19.50
(MSVC 14.50, as `build/cuda-verify-0928`). Prepared on a shared machine by the unit (Opus 5.5); timed on a quiet one
by the orchestrator. Kit, sources and results: `2026-10-08-xl-x86-lanes-128/`.

**Question.** On x86-64, with `dtw_lanes<T>` = 128 / sizeof(T) (four ymm chains per DP row step where 64 bytes run
two), is every lane result unchanged, does each compiler's lanes loop stay free of calls and of spills on the carried
values, and is the fill faster by the registered band?

**Registered band (the orchestrator's, fixed before any run, verbatim):** "per compiler: the candidate is adopted for
that compiler only if every single-thread lanes shape is ≥ 1.10×, both 24-thread equal-length fills are ≥ 1.10×, the
ragged fill stays within 0.97–1.03×, and the outputs are bitwise equal; otherwise that compiler keeps 64 bytes
(FALSIFIED for it). Also reported, no band: whether f64 L1 unbanded reaches V3's prediction (about 2×)." Before any
timing: "A spill or reload added on a loop-carried value (left/diag/up) disqualifies that compiler's candidate before
timing; a reload of a loop invariant is reported and left to the band."

**Result [confirmed], quiet run 2026-10-08 02:02–02:06: clang++ PASS, cl FALSIFIED.** clang++: the lane function, medians
1.148–1.970× on one thread (every one of the 16 shapes ≥ 1.10×; f64 L1 unbanded 1.715× at L 100 and 1.970× at
L 1000, so V3's "about 2×" is met at L 1000), the 24-thread equal-length fills 1.194× and 1.170×, the ragged
per-pair fill 0.988×, the matrices and the sweep bit for bit. cl: medians 0.762–1.028× on one thread (rounds 0.692–1.053×; f32 0.76–0.84×), fills
0.964× and 0.945×, ragged 1.009×, bit for bit — as the assembly check had disqualified it before timing. So
x86-64 takes 128 bytes under clang only (`6531d1a2`): clang++ and clang-cl; cl keeps 64; GCC keeps 64 until timed.
One cell is wide: clang f32 squared L 100 band 10 is 1.148× by its median but 0.758–1.243× over the rounds, the only
round of the 16 shapes below 1.10× (round 1's candidate ran 0.0841 ns/cell in all five of its measurements, against
0.0513 and 0.0551 in rounds 0 and 2, at 5.34 GHz: a slowdown of that one process, cause not investigated).

## Reading [inferred]

clang's base runs 6.4–7.2 cycles per row step unbanded, its candidate 7.2–7.6 for twice the lanes: the base waits on
the carried `left` (`vminpd` 4 + `vaddpd` 3 cycles in llvm-mca's model, which predicted 7.0 for both and at most
2.0× per cell), and four chains fill that wait — V3's mechanism. Banded L 100 (21 rows a column) gains less
(1.15–1.28×): the candidate's row step costs 7.6–9.4 cycles there, the per-column work weighing more. The 24-thread
fills gain 1.17–1.19×, less than one thread's 1.72× and 1.74× at the same shapes; why (E-cores, the DP row's memory traffic,
128 KB a column at L 1000, the fill's other work) is not measured. cl's lanes are scalar and already throughput-bound (30 cycles
per f64 row step), so more chains cost instructions and stack traffic without hiding anything.

## Assembly [confirmed]

clang: `-S -masm=intel` of `dtw_lanes.cpp` with its own flags from `compile_commands.json` (`-O3 -march=native`, the
FP subset, `-fno-lto` as `dtwc/core/CMakeLists.txt` compiles it). The kit's `dtw_lanes.obj` disassembles identically
to the tree's `dtw_lanes.cpp.obj` (anonymous-namespace hash aside), and that native object is what `dtwc_cl.exe`
links. cl: `/FAs` with the CUDA tree's flags minus `/GL` (a `/GL` object holds no code), checked against the
LTCG-linked code (the probes relinked with `/MAP`, disassembled with names: `kit/tools/msvc_dis.py`, `loops.py`):
the same instruction and memory-operand counts, and the base probe's 8 lanes loops are in the tree's `dtwc_cl.exe`
instruction for instruction (`msvc_loops_match.py`). One DP row step = one `i` of the kernel's inner loop; the L1 main
loops are in `asm/`.

| loop | base (W 8 doubles / 16 floats) | candidate (W 16 / 32) |
| --- | --- | --- |
| clang f64 L1 | ymm `vminpd`, 36 instructions per 2 row steps = 18 per row step (2.25/cell); no call, no spill | ymm, 38 per row step (2.38/cell); no call; left, diag in registers; 1 folded reload of a y vector (loop invariant) |
| clang f64 squared | ymm, 35 / 2 = 17.5 (2.19/cell) | ymm, 38 (2.38/cell); 1 reload of a y vector (invariant) |
| clang f32 L1 | ymm `vminps`, 22 (1.38/cell) | ymm, 37 (1.16/cell); 2 folded reloads of y vectors (invariant) |
| clang f32 squared | ymm, 35 / 2 = 17.5 (1.09/cell) | ymm, 37 (1.16/cell); 1 folded reload of a y vector (invariant) |
| cl f64 L1 | scalar `vminsd`, 134 (16.75/cell), 82 memory operands; every lane's diag on the stack, left for 4 of 8 lanes | scalar, 262 (16.4/cell), 174 memory operands; diag 16 of 16, left 8 of 16; y of 13 of 16 lanes reloaded |
| cl f32 L1 | scalar `vminss`, 257 (16.1/cell), 171 memory operands; left on the stack for 5 of 16 lanes | a loop over 4 blocks of 8 lanes per row step: 4 × 132 = 528 (16.5/cell), 4 × 97 memory operands; left, diag, y of all 32 lanes stored and reloaded every row step: **added on the carried `left`** (disqualified) |

No lanes loop of either compiler calls anything. cl's inner min is `std::min`'s reference form: `vcomisd` + `cmovbe`
on the addresses of `up` and `diag`, both stored to stack temporaries, then `vminsd` through the pointer.
`test_codegen_no_calls`: base `inner_loops=154 calls=0 PASS`, every pb/XL commit `inner_loops=142 calls=0 PASS` (the
probe's packing loop over the lanes, unrolled per lane or not: f64 36 → 68 inner loops, f32 52 → 8).
GCC 13.3 (`-O3 -march=x86-64-v3`, the FP subset and `-fno-signaling-nans`: the Linux wheel's flags; assembly only):
at 64 bytes its f64 lanes are scalar (16 `vminsd` per row step, 72–74 instructions, 14–20 stack operands), at
128 bytes packed ymm (33–37 instructions, no stack); f32 packed at both. Worth timing before GCC follows clang.
