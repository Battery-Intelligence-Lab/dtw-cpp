**Question.** `mip-solvers` (the object library of `mip_Gurobi.cpp`, `mip_Highs.cpp`, `lagrangian_root.cpp`) compiled without the OpenMP flag on AppleClang and GCC, so
`_OPENMP` was undefined in `lagrangian_root.cpp` and both `#pragma omp parallel for` loops of `evaluate_dual` compiled out: the Lagrangian phase of `-m lrcore` ran serial in
every clang/GCC build. Do one flag and one definition on that library put the loops back, in every target that links it, with every result bit-identical?

**Answer (phase 1).** Yes on all three [confirmed]. Of 127 compile lines in 104 targets (the libraries, `dtwc_cl`, the MEX, 88 test executables, examples, benchmarks), the
only translation unit with OpenMP content compiled without the flag was `lagrangian_root.cpp`; after the change none is, and exactly three compile lines differ (the three
`mip-solvers` files, each by `-DDTWC_HAS_OPENMP -isystem …/libomp/include -Xclang -fopenmp`). The linked `dtwc_cl` has `evaluate_dual` plus two `.omp_outlined` regions where base
has `evaluate_dual` alone. 33 of the record's 34 inputs, HiGHS ON and OFF, 1 and 18 threads: 330 comparisons of base against head and of the two thread counts, 0 different
(Y6 by the CLI: identical). Serial ctest 95 = 94 passed + 1 skip (CUDA), both trees; conformance output identical; the CLI's 25 runs identical; pytest 922 / 12 / 0 as base.

## The change (`54fe1150` and `96de8de4` on `pb/lr-omp`)

- `dtwc/CMakeLists.txt` (+6): inside `if(OpenMP_CXX_FOUND)`, next to `dtwc_core`'s own: `target_compile_definitions(mip-solvers PRIVATE DTWC_HAS_OPENMP)` and, outside MSVC,
  `target_link_libraries(mip-solvers PRIVATE OpenMP::OpenMP_CXX)`. On MSVC `/openmp:experimental` already reaches `mip-solvers` through `dtwc_options`, so only the definition
  is new there. The `DTWC_ALLOW_SEQUENTIAL` and fatal branches are untouched. The call is made from the parent directory (CMP0079 NEW under `cmake_minimum_required(3.26)`).
  `dtwc_core` keeps the PUBLIC definition and target the consumers need, and the configuration summary (`CMakeLists.txt:423`) still reads it there.
- `dtwc/mip/lagrangian_root.cpp`: `[[maybe_unused]] constexpr index_t kParallelMinN` (the attribute, because a sequential build never reads it) and `if(N >= kParallelMinN)` on
  both pragmas. **The value is a placeholder, 1 (fork at every N)**, so the proofs below exercise the parallel path at every N from 25 up; phase 2 sets it from the sweep
  (the earlier scratch build ran 0.36× at N = 200). The second commit adds a compile-time guard, `#if defined(DTWC_HAS_OPENMP) && !defined(_OPENMP)` → `#error`, the one reader the new
  definition has: if someone drops `OpenMP::OpenMP_CXX` from `mip-solvers` again the build stops, where before it only got slower. It is separate so that it can be dropped alone.

**The two loops, read** (`lagrangian_root.cpp`, `evaluate_dual`) [confirmed]. Loop 1 gives each `i` its own local sum `s` over `j` in the serial order and writes `rho[i]`; loop 2
gives each `j` an integer count over the `k` open rows and writes `g[j]`. Neither reads what the other iterations write, and neither is a reduction; the code between them
(`nth_element`, the two sums) runs on the master thread after the first region's barrier. So a thread count cannot change a bit. What can differ is the code the compiler
emits for the outlined body under `-fassociative-math`; the next sections test that, not argue it.

## The kit (phase 2; not committed, in the session scratch)

`…/scratchpad/lr-omp-timing/`, one command: **`./run.sh`** (`./run.sh smoke` for a check that it runs). Four probes (base / head × HiGHS ON / OFF) built by `build_kit.py` from `ninja -t commands
dtwc_cl` of four trees: base b36fad43 (a `git archive`, built in the scratch) and this worktree's `build/` and `build-nohighs/`. The head probes link a scratch copy of the tree's own
`lagrangian_root.cpp` (compiled with the tree's own flags for that file) whose constant is replaced by `LR_OMP_MIN_N` (default: the product's value): the threshold is a run-time
knob in the probe only. `run.py` interleaves base and head (A B, B A, …) over N ∈ {100, 200, 400, 800, 1600, 3200}, two regimes (`noise`: four templates + N(0, 0.5), k = 4, the record's
C / X1 / Z2; `line`: constant series on a line metric, k = 3, the record's Y1–Y6), HiGHS OFF and ON, `REPEATS` = 3, 18 threads, and prints per cell the root, the LR phase (`lagrangian_root_exact`),
`Problem::cluster()` and the `dtwc_cl` wall time, base against head and the ratio (> 1: head faster), the iteration and node counts, whether each pair was bit-identical, and the four bands.
A stage shorter than `MIN_MS` is repeated inside the probe and reported as its fastest call. `HEAD_LOOP2=0` (a second scratch knob) keeps the second loop serial, for the experiment the one
constant cannot make; `run.py` also prints the crossover N per (flavour, regime). Smoke runs (N = 100, 200, one repeat, load 21–46, so their numbers are not evidence): the kit ran end to
end, 8 of 8 pairs bit-identical, the bands were evaluated (and failed, as a placeholder of 1 at N ≤ 200 and a loaded machine should).
Cost: roughly an hour (the line regime's serial base at N = 1600 and 3200 is minutes per run), so `REPEATS`, `SIZES`, `E2E=0` are knobs.

## Not run, and open

- Linux/GCC, Windows (MSVC, clang-cl, clang's GNU frontend with the MEX's `libiomp5md`), CUDA, the MEX (built nowhere here), ThreadSanitizer. The CMake reasoning for those is [inferred]: the call is
  the same `OpenMP::OpenMP_CXX` that `dtwc_core` already links PUBLIC, which the MEX and the wheel already carry. Bit identity is shown for this build (AppleClang, AArch64): under `-fassociative-math`
  another compiler or target could in principle emit the outlined body's inner sum with another vector shape than the serial one, so Linux and Windows should repeat the probe matrix.
- The second loop's cost is N·k against the first's N², so one threshold on both may fork it where it cannot pay (a fork is about 80 µs at 18 threads: the placeholder run took 2.8 ms for 17 iterations
  at N = 25, against 0.023 ms serial; an observation, not a measurement). Phase 2's sweep shows whether it needs its own bound.
- Phase 2 (when the machine is quiet), the rule registered here before any sweep: run the kit with `HEAD_MIN_N=1` (every N forks); `kParallelMinN` = the smallest swept N from which every
  (flavour, regime) root ratio is ≥ 1.0 (`run.py` prints it; sizes between it and the swept N below it can be added through `SIZES` to narrow it); set it, rebuild, repeat the proofs
  (CLI 25, conformance, ctest, the probe matrix: the `if` clause now takes the serial branch below the value), run the kit with `HEAD_MIN_N` = that value, judge it against the four bands,
  write the CHANGELOG line with the measured numbers. A FALSIFIED band is a result: the record then says which, and what the loops cost where they lose.
