**Question.** `mip-solvers` (the object library of `mip_Gurobi.cpp`, `mip_Highs.cpp`, `lagrangian_root.cpp`) compiled without the OpenMP flag on AppleClang and GCC, so
`_OPENMP` was undefined in `lagrangian_root.cpp` and both `#pragma omp parallel for` loops of `evaluate_dual` compiled out: the Lagrangian phase of `-m lrcore` ran serial in
every clang/GCC build. Do one flag and one definition on that library put the loops back, in every target that links it, with every result bit-identical?

**Answer.** Yes on all three parts of the question [confirmed]. Of 127 compile lines in 104 targets (the libraries, `dtwc_cl`, the MEX, 88 test executables, examples, benchmarks), the
only translation unit with OpenMP content compiled without the flag was `lagrangian_root.cpp`; after the change none is, and exactly three compile lines differ (the three
`mip-solvers` files, each by `-DDTWC_HAS_OPENMP -isystem …/libomp/include -Xclang -fopenmp`). The linked `dtwc_cl` has `evaluate_dual` plus two `.omp_outlined` regions where base
has `evaluate_dual` alone. 33 of the record's 34 inputs, HiGHS ON and OFF, 1 and 18 threads: 330 comparisons of base against head and of the two thread counts, 0 different
(Y6 by the CLI: identical). Serial ctest 95 = 94 passed + 1 skip (CUDA), both trees; conformance output identical; the CLI's 25 runs identical; pytest 922 / 12 / 0 as base. Phase 2 (quiet machine, 18 threads, bands registered before the sweeps): the HiGHS-OFF subgradient root is **3.5–7.3× faster at N = 800–3,200** (B1, ≥ 2×: PASS) and
`dtwc_cl -m lrcore` 1.4–4.7× faster end to end (3,200 series on a line metric: 45.9 s → 10.5 s); no cell of the sweep is below 0.95× (B2: PASS, lowest 0.963); the HiGHS-ON Kelley root is 1.17–1.49× faster at
N ≥ 800 and not below 0.963 anywhere (B3: PASS); every pair is bit-identical (B4: PASS, 54 of 54 cells). `kParallelMinN` = 280. Two findings shaped the final code: forking the second loop never paid
(1.0–2.0× faster without it, so it is left serial: a **flagged deviation** from the brief's one constant on both pragmas), and the base and head trees' own `libhighs` differ by 1–3 % in speed (the kit now loads one). Merged with design-2.0 (48 commits later): zero warnings, ctest 94 = 93 + 1 skip, conformance and `-m lrcore` identical to design-2.0's own tip, pytest 895 / 11 / 0.

## The change (phase 1: `54fe1150`, `96de8de4`, `3bc08848`; phase 2: `6afaafdd`, on `pb/lr-omp`)

- `dtwc/CMakeLists.txt` (+6): inside `if(OpenMP_CXX_FOUND)`, next to `dtwc_core`'s own: `target_compile_definitions(mip-solvers PRIVATE DTWC_HAS_OPENMP)` and, outside MSVC,
  `target_link_libraries(mip-solvers PRIVATE OpenMP::OpenMP_CXX)`. On MSVC `/openmp:experimental` already reaches `mip-solvers` through `dtwc_options`, so only the definition
  is new there. The `DTWC_ALLOW_SEQUENTIAL` and fatal branches are untouched. The call is made from the parent directory (CMP0079 NEW under `cmake_minimum_required(3.26)`).
  `dtwc_core` keeps the PUBLIC definition and target the consumers need, and the configuration summary (`CMakeLists.txt:423`) still reads it there.
- `dtwc/mip/lagrangian_root.cpp`, final (`6afaafdd`): `[[maybe_unused]] constexpr index_t kParallelMinN = 280` (the attribute, because a sequential build never reads it) and `if(N >= kParallelMinN)` on
  the pragma of loop 1 (`rho`, N² work); loop 2 (`g`, N·k work) has no pragma. Phase 1 landed the constant as a placeholder, 1 (fork at every N), with the `if` on both pragmas, so that its proofs exercise the
  parallel path at every N from 25 up; phase 2 (below) measured it. The guard's commit (phase 1) adds a compile-time guard, `#if defined(DTWC_HAS_OPENMP) && !defined(_OPENMP)` → `#error`, the one reader the new
  definition has: if someone drops `OpenMP::OpenMP_CXX` from `mip-solvers` again the build stops, where before it only got slower. It catches the target dropped with the definition kept, not
  both dropped. It is separate so that it can be dropped alone; the third commit adds `&& !defined(__CPPCHECK__)`: cppcheck (`DTWC_DEV_MODE`, `cmake/StaticAnalyzers.cmake`) takes the target's `-D`
  but no compiler flag, so it never sees `_OPENMP`, and its `--suppress=preprocessorErrorDirective` (line 28) would have skipped the file without a word (the adversarial review's finding; cppcheck is
  not installed here, so that clause is read, not run).

**The phase-1 state was not mergeable alone, and phase 2 replaced it.** At the placeholder every fork happens at every N, and the repo's own LR tests solve dozens of instances at N = 6–14 (`tests/unit/mip/test_lagrangian_root.cpp:214–372`), the adversarial ones up to the 4000-iteration cap: `test_lagrangian_root` ran 17.5 s (ON) and 20.8 s
(OFF; the two trees concurrently, load 40–58 from other agents) against 0.45 s at base (the orchestrator's `ctest-w13c.log:29`), `test_reduced_cost_fixing` 12.9 / 12.3 s against 0.28 s (this unit's
`ctest-head-on.guard1.log`, `ctest-head-off.guard1.log`, lines 29 and 95); the first, less loaded ON run had `test_lagrangian_root` at 8.0 s (that log was overwritten by the rerun). On a loaded machine, so not a
measurement, but the sign and the order are what a fork of about 80 µs per loop per iteration at N = 25 predicts (2.8 ms against 0.023 ms for 17 iterations). The placeholder bought the phase-1 proofs their coverage (ctest and `07_lrcore` ran the parallel branch).

**The two loops, read** (`lagrangian_root.cpp`, `evaluate_dual`) [confirmed]. Loop 1 gives each `i` its own local sum `s` over `j` in the serial order and writes `rho[i]`; loop 2
gives each `j` an integer count over the `k` open rows and writes `g[j]`. Neither reads what the other iterations write, and neither is a reduction; the code between them
(`nth_element`, the two sums) runs on the master thread after the first region's barrier. So a thread count cannot change a bit. What can differ is the code the compiler
emits for the outlined body under `-fassociative-math`, so the disassembly was opened [confirmed]: on AArch64 the inner sum of loop 1 is the same scalar chain
`ldr d1 ← D[i][j]; ldr d2 ← mu[j]; fsub; fadd d2, d1, d0; fcmp d1, #0; fcsel d0, d2, d0, mi` in base's serial body (`evaluate_dual`, `0x10007eaac–0x10007eac0` in the
`base-build` binary) and in head's outlined body (`evaluate_dual.omp_outlined`, `0x10007f634–0x10007f648`): no vector reassociation in either, so each `rho[i]` is summed in the order j = 0…N−1
in both, and the 330 comparisons below are what that predicts. Loop 2 is an integer count (serial in the final design; this reading is what the phase-1 proofs rested on).
